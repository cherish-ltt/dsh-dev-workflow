# Issue to PR — Issue 修复与 PR 交付

## 一、核心目标

以项目 Issue 为任务来源，完成完整开发闭环：

Issue 梳理 → 范围确认 → 协作状态检查 → Issue 认领 → 修复规划 → 创建分支 → 实施修改 → 测试验证 → Commit → Push → 创建 PR。

执行原则：
1. 用户明确指令优先于本 Skill 默认规则。
2. 以 Issue、项目文档及真实代码为依据，不臆测需求。
3. 修复范围最小化，不进行无关重构。
4. 每个独立修复单元使用独立分支和 PR。
5. 关联 Issue 可以合并到同一个修复分支和 PR。
6. 修复必须经过适当测试验证。
7. PR 描述标准化，方便维护者快速审阅。
8. 不擅自合并 PR、发布版本或部署项目。

## 二、项目与 Git 平台探索

识别项目实际使用的 Git 托管平台，确认对应连接器、CLI/API 是否可用，以及是否具备必要的读取和写入权限。

探索：
- 项目目录、技术栈及入口文件。
- AGENTS.md、README、架构文档及开发规范。
- 核心模块、调用链及业务流程。
- 现有测试及执行方式。
- Git 仓库、当前分支、工作区状态及远端信息。
- 项目 Issue、PR 模板、标签及分支规范。

要求：
- 只探索与任务相关的内容。
- 不臆测文件路径、接口签名及既有行为。
- 优先阅读真实实现、相关测试和项目约定。
- 不覆盖用户已有修改。
- 不绑定特定 Git 托管平台。

## 三、Issue 范围确认

读取项目符合任务范围的 Issue，检查：

- 标题、正文、优先级及标签。
- 评论及补充要求。
- 关联 Issue、PR 和 Commit。
- 当前开放、关闭及处理中状态。

如果用户已经明确指定 Issue，按指定范围处理。

如果用户没有明确指定范围，先展示 Issue 清单，询问用户：
- 处理全部符合条件的未完成 Issue。
- 仅处理指定 Issue。

不得擅自重新打开已关闭的 Issue。

### Issue 分类

优先遵循项目现有分类和优先级规范。

识别：
- Bug / Defect：功能缺陷。
- Enhancement：功能增强及体验改进。
- Security：安全问题。
- Performance：性能问题。
- Maintenance：工程维护及技术债务。

P0/P1/P2/P3 的含义以项目规范为准，不得自行混淆优先级和问题类型。

### Issue 理解

每个 Issue 必须明确：
1. 当前问题及预期行为。
2. 产生原因及影响范围。
3. 涉及模块及现有实现。
4. 修复范围及约束条件。
5. 可验证的完成标准。

如果 Issue 与实际代码、文档存在冲突，或存在影响实现方向的重要歧义，向用户询问。

## 四、Issue 协作状态检查与认领

**这是每个 Issue 开始修复之前的强制步骤。**

目的：避免多个开发者、Agent 或自动化工作流同时处理同一个 Issue，产生重复 PR、代码冲突及重复劳动。

### 1. 开工前检查

逐个 Issue 检查：

- 是否已经存在关联 PR，包括 Draft PR。
- 是否存在其他工作者提交的相关 PR。
- 是否存在引用该 Issue 的 Commit。
- 是否存在以该 Issue 命名的修复分支。
- Issue 是否已经被指派给其他工作者。
- 是否存在 `in-progress` 等处理中标签。
- 评论区是否有其他工作者的认领声明。
- 是否存在尚未完成的实现或 Review 工作。

不能只依赖 Issue 评论，还应检查 PR、分支及提交记录。

### 2. 处理已有工作

| 当前状态 | 处理方式 |
|---|---|
| 已存在已合并 PR，Issue 已解决 | 标记已完成，跳过 |
| 已存在其他人的开放 PR | 不重复修复，记录 PR 链接 |
| 已存在自己的开放 PR | 继续原有分支和 PR |
| 已存在其他人的有效认领 | 暂停，不擅自抢占 |
| 存在未完成分支或 Commit | 调查归属和进度，不覆盖 |
| 没有认领及相关工作 | 可以认领并开始修复 |

如果发现其他工作者已经认领：
- 不得直接修改其正在处理的同一问题。
- 不得创建重复 PR。
- 如果无法判断认领是否仍然有效，询问用户。
- 不得擅自认定其他工作者的认领已经过期。

### 3. 认领 Issue

确认没有其他有效工作者处理后，必须先认领，再开始修改代码。

优先遵循项目已有的协作规范，选择合适方式：

1. 将 Issue 指派给当前已认证的工作身份。
2. 添加项目已有的处理中标签。
3. 在 Issue 评论区发布认领声明。

如果项目没有现成机制，优先使用评论认领。

推荐评论格式：

**认领声明**

- 处理者：当前已认证的工作身份。
- 状态：开始处理。
- 计划：简述本次修复目标。
- 预计分支：修复分支名称。
- 关联 PR：创建后补充链接。

必须确认认领操作实际成功后才能开始修改代码。

注意：
- 不得冒用其他用户身份。
- 不得擅自覆盖其他人的指派或认领。
- 如果没有认领权限，停止该 Issue 的代码修改，向用户报告。
- 多个 Issue 合并处理时，必须先检查并认领所有关联 Issue。

### 4. 更新认领状态

修复过程中：
- 保持 Issue 处于处理中状态。
- PR 创建后，在 Issue 评论中补充 PR 链接。
- 按项目约定更新标签或工作状态。
- PR 合并后，按平台及项目规范关闭 Issue。

如果修复中断或无法继续：
- 如实更新阻碍状态。
- 保留已有分支及 Commit。
- 不得让 Issue 长期处于错误的处理中状态。

## 五、制定修复计划

完成 Issue 梳理和协作状态检查后，制定整体执行计划。

考虑：
1. 问题严重程度。
2. Issue 之间的依赖关系。
3. 相同根因及代码修改范围。
4. 修复风险及测试成本。
5. 项目架构和设计约束。

优先处理高严重程度问题，再处理一般缺陷和改进需求；依赖关系优先于简单的优先级排序。

### Issue 合并原则

多个 Issue 可以合并到同一个 PR，但必须满足：
- 具有相同或高度关联的根因。
- 修改范围高度重叠或属于同一完整功能。
- 可以通过一致的测试验证。
- 合并后仍然容易审阅。

不同根因、不同模块或无关改进不得为了减少 PR 数量而合并。

### 执行计划

| 顺序 | Issue | 类型 | 优先级 | 修复范围 | PR 分组 |
|---|---|---|---|---|---|
| 1 | #N | Bug | P1 | 模块 A | PR-1 |
| 2 | #N | Bug | P1 | 模块 B | PR-2 |
| 3 | #N、#N | Enhancement | P2 | 模块 C | PR-3 |

## 六、逐项实施修复

每个独立修复单元严格遵循以下流程。

### 1. 创建修复分支

- 确认目标基础分支。
- 获取最新远端信息。
- 检查工作区及现有分支。
- 从合适的基础分支创建修复分支。
- 遵循项目现有分支命名规范。

没有现有规范时：

- `fix/<issue-id>-<description>`
- `feat/<issue-id>-<description>`
- `refactor/<issue-id>-<description>`

多个 Issue 合并时，使用能够概括共同修复目标的分支名称。

禁止直接在基础分支实施修复。

### 2. 探索真实实现

修改之前：
- 阅读相关代码及完整调用链。
- 查阅项目开发规范。
- 检查相关测试和已有实现。
- 确认问题根因及最小修改范围。
- 检查兼容性、数据迁移及外部接口影响。

不得仅凭 Issue 描述直接修改代码。

### 2.1 最小化复现与真实性确认

**这是每个 Issue 开始正式修复前的必要阶段。先证明问题存在，再实施修复。**

根据 Issue 描述，优先使用临时代码、独立测试脚本或自动化测试构造最小复现。

执行步骤：

1. 根据 Issue 描述确定触发条件、预期行为及实际行为。
2. 尽可能剥离无关依赖和业务逻辑，构造最小复现环境。
3. 编写临时测试代码或测试用例，尝试复现问题。
4. 实际运行，观察结果是否符合 Issue 描述。
5. 确认问题真实存在后，再进入正式修复阶段。

要求：

- 优先使用测试代码复现，避免直接修改正式业务代码。
- 复现代码应尽可能短小、独立且容易理解。
- 区分 Bug 的实际错误行为与 Enhancement 尚未实现的预期行为。
- 如果无法复现，不得直接认定 Issue 描述错误，应检查环境差异、触发条件及隐藏依赖。
- 如果证据不足或无法确认，应暂停该 Issue 的修复，向用户说明原因。
- 不得为了让测试通过而修改正式业务代码或篡改预期结果。

### 复现代码的保留

成功复现问题的临时代码，应评估是否适合作为正式回归测试：

- 能够稳定复现、具有长期回归价值且符合项目测试规范的，保留并纳入正式测试。
- 仅用于临时环境搭建、诊断或不适合长期维护的代码，在完成验证后清理。
- 保留的测试应验证问题修复前失败、修复后通过，确保能够防止同类问题再次发生。

**原则：先复现，再修复；先证明问题，再提交修改。**

### 3. 实施修复

- 采用最小必要修改。
- 遵循现有架构和代码风格。
- 不引入无关功能。
- 不进行无关重构。
- 必要时增加或修改自动化测试。
- 评估接口、数据结构和兼容性影响。

### 4. 测试验证

根据修改内容选择：

- 单元测试。
- 集成测试。
- 端到端测试。
- 类型检查及静态分析。
- Lint 和格式检查。
- 必要的性能或兼容性测试。

要求：
- 优先执行直接相关的测试。
- 根据风险决定是否运行完整测试套件。
- 测试失败必须调查根因。
- 区分原有失败和本次修改引入的失败。
- 不得伪造测试结果。
- 不做无意义的重复测试。

### 5. 代码自审

提交前检查：
- 是否完整解决 Issue。
- 是否引入新 Bug。
- 是否存在无关修改。
- 是否遗漏边界条件。
- 测试是否覆盖关键行为。
- Diff 是否清晰精简。
- 是否包含敏感信息或调试代码。

### 6. Commit

- 只暂存本次修复相关文件。
- 遵循项目 Commit Message 规范。
- 提交前检查暂存区 Diff。
- 不得擅自修改 Git 用户身份或签名配置。

## 七、Push 与创建 PR

完成修改、测试及 Commit 后：

1. 推送修复分支。
2. 检查远端分支及最新 Commit。
3. 再次检查是否已经存在相同目的的 PR。
4. 创建对应 PR。
5. 检查 PR 标题、正文、目标分支和关联 Issue。
6. 确认平台返回的实际创建结果。

如果发现其他工作者在修复期间已经创建了相关 PR：
- 立即停止重复创建。
- 比较双方修改范围。
- 判断是否存在重复实现或冲突。
- 向用户报告并确认后续处理。

禁止：
- 强制覆盖远端分支。
- 未经授权合并 PR。
- 修改保护分支规则。
- 擅自发布版本或部署。
- 在权限不足时伪造成功状态。

## 八、PR 标准化描述

遵循项目现有 PR 模板。没有模板时，统一使用以下结构。

### 标题

使用项目约定的格式，清晰描述修改目的。

例如：

`fix: prevent duplicate transaction processing`

### 正文模板

#### 1. 一句话概述

一句话说明本 PR 解决什么问题、带来什么变化。

#### 2. 问题背景

说明原有问题、触发条件及影响。

#### 2.1 Issue 最小复现

提供能够证明原始 Issue 确实存在的最小复现证据。

根据复现代码长度选择合适的展示方式：

- **短代码**：直接在 PR 正文中使用代码块展示，包含必要的输入、执行方式及实际结果。
- **长代码**：简要说明复现步骤，并提供对应的测试代码文件路径。
- **复杂环境**：说明前置条件、环境配置、执行命令及观察到的结果。

要求：

- 尽可能展示修复前的实际错误行为。
- 明确区分修复前的实际结果和预期结果。
- 如果复现代码已纳入正式回归测试，提供对应测试文件路径及测试名称。
- 复现代码应精简，避免将大量无关实现粘贴到 PR。
- 不得提供未经实际验证的复现代码或虚构测试结果。

目的：让 PR 审阅者能够快速理解问题、独立验证问题，并确认本次修改确实解决了 Issue。

#### 3. 修改内容

说明：
- 修改模块。
- 核心实现方案。
- 方案选择原因。
- 接口、数据结构及兼容性变化。

#### 4. 关联 Issue

列出所有关联 Issue。

仅在确认该 PR 合并后应该关闭对应 Issue 时，使用 `Closes`、`Fixes` 等自动关闭关键词；否则使用普通引用。

#### 5. 测试与验证

列出：
- 执行的测试命令。
- 测试结果。
- 新增或修改的测试。
- 未执行的测试及原因。

#### 6. 风险与兼容性

说明行为变化、兼容性影响、数据迁移及部署要求。

没有特殊风险时明确说明。

#### 7. 审阅重点

指出维护者需要重点检查的修改及关键文件。

UI 修改应提供必要截图或演示。

#### 8. 检查清单

- [ ] 修改符合 Issue 预期。
- [ ] 已完成适用的测试。
- [ ] 已检查代码 Diff。
- [ ] 无无关修改。
- [ ] 必要文档已更新。
- [ ] 已评估兼容性及风险。

#### 9. 署名

`署名：{用户确认的文本}`

如果用户没有提供或确认署名，必须询问。

不得自行使用模型名称、开发者名称或其他身份。

署名只作为 PR 正文内容，不得擅自修改 Git Commit Author 或提交者身份。

## 九、PR Review 与后续处理

PR 创建后：
- 检查 PR URL、编号及目标分支。
- 检查 CI/CD 状态。
- 检查 Review 评论及修改要求。
- 必要时继续在原分支修改并更新原 PR。

如果出现新的需求或超出原 Issue 范围的修改，向用户确认。

不得为同一个修复重复创建 PR。

PR 创建不代表 Issue 已解决，只有达到项目规定的完成状态（通常为 PR 合并）才能标记为已完成。

不自动合并 PR。

## 十、执行策略

### 自主执行

对于用户明确授权的范围：
- 自主探索、认领、修改、测试、Commit、Push 和创建 PR。
- 不因普通实现细节反复询问。
- 能够从项目约定推断的内容直接采用。
- 只有真正影响实现方向的问题才询问。

### Subagent 委派

如果具备 Subagent 工具，可以委派：
- 独立 Issue 的代码探索。
- 根因分析。
- 测试方案设计。
- 独立代码审查。

要求：
- 每个 Agent 明确任务范围。
- 主 Agent 统一决策和最终验证。
- 避免多个 Agent 同时修改同一工作区。
- 同一个 Issue 同一时间只能由一个明确认领的工作者负责。
- 只有在工作区隔离、Issue 独立且已经分别认领时，才考虑并行实施。

没有 Subagent 时正常顺序执行。

## 十一、最终汇报

### 1. 总体进度

| 状态 | 数量 |
|---|---:|
| 已创建 PR | N |
| 已合并 | N |
| 处理中 | N |
| 待用户确认 | N |
| 受阻 | N |

### 2. Issue 与 PR 对应关系

| Issue | 修复内容 | 分支 | PR | 状态 |
|---|---|---|---|---|
| #N | 问题描述 | branch-name | PR 链接 | 已创建 |

一个 PR 关联多个 Issue 时，完整列出所有关联编号。

### 3. 测试结果

列出关键测试及结果，说明失败、跳过和未执行的项目。

### 4. 遗留事项

说明未处理 Issue、未完成 PR、CI/Review 待处理事项及需要用户决策的问题。

### 5. 最终验收

- [ ] 已确认 Issue 处理范围。
- [ ] 已检查已有 PR、分支及其他工作者的进度。
- [ ] 每个 Issue 开工前均已成功认领。
- [ ] 已制定合理修复计划。
- [ ] 每个独立修复单元均使用独立分支。
- [ ] 已完成必要代码修改和测试。
- [ ] 已完成提交前自审。
- [ ] 已创建对应 PR。
- [ ] PR 使用统一描述结构。
- [ ] PR 署名使用用户确认的文本。
- [ ] 已检查 PR 创建结果及 CI 状态。
- [ ] 未擅自合并 PR。
- [ ] Issue 状态及认领信息已及时更新。

**最终原则：先检查是否有人在做，再认领 Issue，然后实施修复。以 Issue 为任务单位，以分支隔离修改，以测试证明修复，以 PR 交付结果。避免重复劳动，确保每个 Issue 都有明确的负责人和处理状态。**
